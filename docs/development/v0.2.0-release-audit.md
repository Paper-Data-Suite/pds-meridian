## Preliminary substantive findings

### Teacher-controlled grouping policy — CONFORMS

Inspection of `meridian.grouping_signal_policy` confirms the accepted v1
fairness boundary:

- the only tie-handling mode is `same_level_same_band`;
- missing and insufficient results use only explicit `noncontributing` or
  `blocking` handling;
- policy band definitions are explicit;
- policy state remains separate from derivation, Core export, and Concord
  Group formation.

Focused release-audit regression coverage freezes the closed tie/result
handling vocabulary.

### Missing-result planning semantics — CONFORMS

Inspection of `meridian.grouping_signal_generation` and
`meridian.grouping_signal_derivation` confirms:

```text
missing source
    -> noncontributing derivation
    -> no proficiency level
    -> no scale position
    -> no band
```

The immutable student-derivation contract rejects an attempt to encode a
missing result as Band 1. This preserves:

```text
missing != low proficiency != lowest planning band
```

The same production path keeps insufficient evidence noncontributing unless
the selected teacher policy explicitly blocks the class derivation.

### Concord group-target evidence — CONFORMS

Inspection of `meridian.concord_adapter` confirms that a Concord result whose
actual target is `concord_group` projects as nonstudent evidence. Student
identities appearing elsewhere in provenance do not rewrite that target into
an individual student subject.

Focused release-audit regression coverage invokes the real Concord adapter
over the existing synthetic released-contract fixture and requires every
group-target item to retain `subject is None`.

### Planning-runtime Concord dependency — CONFORMS

The Meridian `grouping_signal*.py` runtime family is the producer-side
planning-signal path. Focused release-audit coverage parses those runtime
modules and rejects direct imports from Concord, `pds_concord`, or
`meridian.concord_adapter`.

This protects the accepted handoff:

```text
Meridian
    -> Core grouping_signal_set_v1
        -> optional downstream planning consumer
```

rather than a direct Meridian-to-Concord planning dependency.

## Privacy, authorization, and export-control audit

### Protected projection-cache reads — CONFORMS

Inspection of `load_authorized_projection_snapshot` confirms that Meridian
invokes the configured projection authorization boundary before opening the
protected cached projection payload.

The audit distinguishes safe metadata/path validation from protected payload
access. The release invariant is:

```text
validate canonical identity / authorization scope
    -> _authorize(..., cache_read=True)
    -> _stored_from_path(...)
    -> bounded protected projection payload read
```

Focused release-audit coverage freezes that ordering around the exact
`payload_path.read_bytes()` operation.

### Grade Item explanation privacy — CONFORMS

The default #34 Grade Item proficiency explanation resolves persisted
Meridian policy/provenance only. It does not open protected projection
evidence.

Native producer/evidence detail is a separate optional expansion:

```text
base explanation
    -> optional expand_grade_item_evidence_detail(...)
    -> diagnostics evidence inspection
    -> authorized projection-cache reader
```

Authorization denial is represented as protected-detail status `denied`;
it is not translated into academic missingness, exclusion, or insufficient
evidence. Missing authorization-provider state is likewise reported as
detail unavailable rather than silently bypassed.

Focused audit coverage freezes the separation between the base explanation
and the authorized-detail resolver.

### Attention and Core-neutral module operations — CONFORMS

Inspection of the Grade Item/Academic Period/planning attention stack and
module-operations façade confirms that these surfaces summarize persisted
Meridian/Core state rather than importing protected projection-cache,
producer-adapter, or raw-evidence paths.

Focused structural coverage guards:

```text
academic_period_attention
planning_attention
proficiency_attention
attention_service
attention_provider
pds_operations
```

against direct imports from the projection cache, EvidenceItem model, or
ScoreForm/Quillan/Concord adapter/runtime packages.

This is a structural privacy guard for the accepted Core-neutral attention
surface; it does not replace the normal authorization requirement on any
separate protected-evidence workflow.

### Core grouping-signal minimality — CONFORMS

Inspection of `grouping_signal_export.py` confirms that Meridian projects
one exact #38 derivation into Core's public `grouping_signal_set_v1` model.

Only contributing student IDs and contextual band assignments cross that
boundary. The Core source binding contains the exact Meridian derivation
identity/digest; it does not serialize Meridian's Grade Item, Standard,
proficiency, attempt, reassessment, teacher-actor, or review-diagnostic
internals.

Existing dynamic export tests already verify forbidden private fields are
absent from Core canonical JSON and that noncontributing students are not
assigned a sentinel/lowest band. Issue #45 additionally verifies both Core
JSON and Core-native CSV round trips in an isolated installed environment.

Focused release-audit coverage guards that the pure projection imports the
Core grouping-signal contract, has no Concord planning import, and performs
no storage write itself.

### Preview/review/export control — CONFORMS

Inspection of `grouping_signal_export_eligibility.py` confirms that export
readiness requires the exact selected current policy/derivation plus the
exact selected review, and that the review decision must be
`accepted_for_export`.

Existing eligibility tests cover:

```text
missing derivation
stale derivation
no selected review
stale selected review
rejected current review
accepted but unselected review
explicitly selected accepted current review
```

Inspection of `export_grouping_signal_to_core` confirms a two-phase
consequential-write boundary:

```text
resolve_grouping_signal_export_eligibility(...)
    -> exact derivation/preview load and Core candidate diagnostics
    -> revalidate_grouping_signal_export_eligibility(...)
    -> write_grouping_signal(...)
```

The final revalidation is deliberately the last read-only authorization
operation before Core persistence. Existing dynamic workflow tests prove
that a final revalidation failure prevents the Core writer from running.

Focused release-audit coverage freezes one initial eligibility resolution,
one final live revalidation, and one Core write in that exact order.

## Producer semantics, calculation, and history audit

### Producer-semantic isolation — CONFORMS

Meridian's proficiency-mapping boundary binds an exact
`NativeValueSourceSignature` rather than interpreting a producer-native value
by shape alone.

The signature carries the producer/publication/projection/reader/result/target
identity needed to distinguish superficially similar evidence. Mapping fails
closed with `source_signature_mismatch` when that exact signature differs.

Focused audit coverage proves that the same native boolean value accepted for
one ScoreForm signature does not cross-apply through a Quillan signature.

Existing mapping coverage additionally proves:

```text
raw points bind exact points_possible
same earned value with another denominator -> unsupported
native scaled values bind exact native scale identity
unmapped native scale levels remain unmapped
native state remains native_state
native state -> no proficiency level
```

Meridian therefore does not normalize producer evidence through a hidden
percentage or generic scalar layer before teacher-authored mapping policy.

### Grade Item proficiency calculation — CONFORMS

The #34 calculator consumes exact immutable #33 aggregation inputs, one exact
proficiency policy, and one exact proficiency scale.

Aggregation strategies operate on declared scale `position`, not lexical
`level_id` order or arithmetic over level identifiers.

Focused audit coverage uses deliberately nonlexical level IDs and verifies
`highest` selects the highest declared position. It also verifies that a
native non-score state plus deliberate exclusion produces
`insufficient_evidence` with no proficiency level rather than the lowest
level.

Existing calculation coverage verifies explicit tie policy for median/mode,
minimum evidence, blocking exclusions, deterministic canonical input
fingerprints, and stable explanation ordering.

### Academic Period proficiency calculation — CONFORMS

The #35 calculator consumes exact Grade Item proficiency-result references and
explicit Academic Period membership basis.

Missing and insufficient Grade Item results remain policy states. Under
`noncontributing`, they do not become the lowest proficiency level; under
`blocking`, they fail the Academic Period calculation explicitly.

Focused audit coverage verifies:

```text
calculated + missing/noncontributing -> calculated from real result only
missing-only/noncontributing -> insufficient_evidence, level None
```

Existing coverage verifies exact scale-position aggregation, explicit
median/mode rules, `period_scope_mismatch` as blocking, deterministic
membership ordering, and preservation of an exact historical Grade Item
result reference when that is the deliberately supplied input.

No current date/time is used to infer Academic Period membership.

### Deterministic immutable result history — CONFORMS

Both #34 and #35 persist immutable contiguous result revisions separately from
their current-selection sidecars.

A result write does not imply current selection.

Focused audit coverage writes two result revisions, verifies that current
remains unset, explicitly selects revision 2, and then deliberately reselects
historical revision 1 through the digest-validated compare-and-swap selection
boundary.

Existing storage suites additionally verify:

- exact replay is idempotent;
- same-revision/different-content writes conflict;
- noncontiguous history fails;
- selected pointers are SHA-bound;
- pointer/revision tampering fails closed;
- result dependencies bind exact policy/scale/Grade Item state.

Issue #45's installed fresh-process acceptance remains the release-level proof
that the persisted #34/#35 and planning provenance chain survives process
restart without substituting newer state.

## Explanation, currentness, and attention audit

### Grade Item and Academic Period explanation selection — CONFORMS

The #34 and #35 explanation surfaces require an explicit target mode:

```text
current
revision
```

`current` resolves only the canonical selected-result pointer. `revision`
resolves the exact requested historical revision.

Existing dynamic explanation suites prove:

- an unselected result does not silently become current;
- an exact historical result remains historical when a newer revision is
  selected;
- `selection_state` distinguishes `selected_current`, `historical`, and
  `no_current_selection`;
- current-target resolution fails closed if the current pointer changes
  during explanation assembly;
- exact missing/tampered provenance edges fail as integrity errors rather
  than being replaced by newer equivalent state.

Focused release-audit coverage freezes the closed `current`/`revision`
target vocabularies.

### Nested historical provenance — CONFORMS

Historical provenance remains historical across explanation layers.

The Academic Period explanation constructs nested Grade Item explanation
targets with `selection="revision"` only.

The planning-derivation explanation constructs nested Academic Period
explanation targets with `selection="revision"` only.

Therefore:

```text
#35 stored #34 reference
    -> exact #34 revision explanation

#38 stored #35 source reference
    -> exact #35 revision explanation
    -> exact nested #34 revision explanation
```

A currently selected newer result is never substituted for one of those
stored historical dependencies.

### Planning derivation and export explanation identity — CONFORMS

Planning explanation targets deliberately have no `current` or `latest`
selector:

```text
PlanningSignalDerivationTraceTarget
    class_id
    derivation_id

PlanningSignalExportTraceTarget
    class_id
    signal_set_id
```

The #38 derivation identity and Core signal-set identity are immutable
content-addressed/exact targets.

Existing planning explanation suites verify the exact policy, scale,
Academic Period result, preview, review, export receipt, and Core signal
lineage. The export explanation uses the exact receipt-bound #39/#38
records and reports the preview currentness state that was recorded for
that export; it does not reinterpret a historical export through whatever
review or derivation is selected now.

### Attention current-vs-historical semantics — CONFORMS

Academic Period attention is defined only over discovered canonical
`current.json` #35 selectors. Missing result families and unselected
historical revisions are explicitly not attention.

Planning attention separately distinguishes:

```text
none
unselected_history
selected_current
selected_rejected
selected_stale
```

Focused audit coverage verifies that:

- current derivation + unselected review history produces
  `planning_review_selection_pending`;
- no current derivation + selected stale review produces
  `planning_review_stale`;
- stale unselected history alone does not create a false current-task
  attention item;
- impossible current/stale review-state combinations fail validation.

Existing dynamic attention suites verify that stale selected Academic
Period targets aggregate once each and malformed current pointers fail
closed.

### Attention privacy and school-year control — CONFORMS

Native Meridian attention remains aggregate and privacy-minimal:

```text
code
count
optional class_id
```

It contains no student identifier or raw academic detail.

The attention service accepts an explicit optional `active_school_year` and
forwards it to both planning and Academic Period inspection. Focused audit
coverage rejects clock-based active-school-year inference in the attention
runtime; existing service coverage proves the explicit school-year value is
forwarded without date inference.

These attention summaries are navigational teacher-workflow cues, not
proficiency, Grades, planning bands, or student labels.

## Release-record / artifact-hash boundary

A release-engineering correction is required before persistent artifact hash
capture.

The durable release audit must eventually record the final sdist SHA-256. An
sdist that contains that audit would be self-referential: inserting the sdist
hash into the audit would change the sdist bytes and therefore change the hash.

The v0.2.0 boundary therefore treats:

```text
docs/development/v0.2.0-release-audit.md
    = repository-only release record
    != source-distribution payload
```
